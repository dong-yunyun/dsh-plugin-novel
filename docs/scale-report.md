# 368 章规模压测报告

> 输入：`流氓高手` 全书 368 章 / 1,176,641 字（≈117 万字）
> 方法：合成卡片（从章文本 + 真实名字词表确定性派生，**不调用模型**），跑完整规则链路
> 隔离：全部产物落 `.scale-sim/`，不触碰生产 `cards/`

---

## 一、性能：不是问题

| 阶段 | 耗时 |
|---|---|
| 合成 368 张卡片 | 62 ms |
| deriveGraph | <1 ms |
| buildBible | 2 ms |
| buildSynopsis | <1 ms |
| buildScreenplay | 3 ms |
| 渲染 368 章注入态 | 4 ms |
| 校验 368 张卡片 | 1 ms |
| **合计** | **72 ms** |
| 内存峰值 | 55 MB |

百万字规模下，**纯规则链路快得可以忽略**。瓶颈只会在模型调用（368 次抽取）。

## 二、token 分布

| 指标 | 值 |
|---|---|
| 单章注入态均值 | **221 token**（31 章实测 223，规模稳定） |
| 368 章注入态合计 | 81,298 token |
| 368 章存储态合计 | 196,482 token |
| 超预算章 | **0** |
| 密度分档 | 低 2 / 中 366 / 高 0 |

**结论：分级预算在全书规模稳定，没有一章越界。** 均值 221 与 31 章样本的 223 几乎一致，说明合成数据没有失真。

## 三、三个会爆的地方

### ① 全书概要 17,955 token —— 超 standard 档 3 倍

368 章的投影型概要合计 **17,955 token**，而 §5.4 定义的 standard 档预算是 6,000。

原因：D 段（剧情脉络）逐章一行、E 段（伏笔账本）全列。**概要不是"全书一档"，必须按"到当前章"裁剪或分卷生成。**

### ② 伏笔账本线性膨胀到 736 条

合成数据每章 2 条 planted、无 paid → 368 章累积 **736 条未回收**。

真实语料会标一部分 paid，但趋势一样：**伏笔只增不减**。概要把 736 条全列出来毫无用处。

需要：
- 按"最近 N 章 + 涉及当前人物"筛选
- 给伏笔加"重要度"或"是否主线相关"
- 超过阈值的旧伏笔自动降级（只留计数）

### ③ 剧本包 135,582 token

368 章一个单元产生 2,208 场，场次表本身就是一本书。

这**印证了设计里的硬边界**：剧本只做单个叙事单元（~100 章），不做全书。真按全书出剧本，单次输出根本装不下。

## 四、产物体积

| 文件 | 大小 |
|---|---|
| `graph.json` | 4 KB（26 节点 / 27 边，受合成词表限制） |
| `bible.json` | 190 KB |
| `synopsis.md` | 75 KB |
| `screenplay.md` | 466 KB |

`bible.json` 190 KB 意味着**不能整份塞进 prompt**，必须按预算截断（当前实现只取前 60 人物）。

## 五、结论

| 维度 | 判定 |
|---|---|
| 规则链路性能 | ✅ 百万字 72ms，可忽略 |
| 注入预算稳定性 | ✅ 368 章全部合规 |
| 概要预算 | ❌ 全书单档会爆 3 倍 |
| 伏笔账本 | ❌ 线性膨胀，需要筛选策略 |
| 剧本范围 | ✅ 设计里的"单元限制"被数据证实必要 |

前两项可以放心；后两项要在 W2 之前补策略，否则全书规模下概要与剧本都不可用。
