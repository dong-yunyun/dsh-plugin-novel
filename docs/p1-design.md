# 网文续写助手 P1 设计（草案）

> 版本 v0.11 ｜ 状态：**W1 进行中（7 章卡片、渲染器已验；节点扫描失败已改单遍）** ｜ 适用范围：DSH Host 插件（当前桌面端 profile）

---

## 1. 背景与问题

用户在 DSH 中粘贴一部网络小说，要求续写或改编剧本。当前做法的成本结构有三个硬伤：

1. **小说以一条用户消息的形式进入会话**，此后每轮全量重发。DSH 的压缩（`dsh-compaction-basic`）在契约上**无法切分单个不可分割单元**，因此这块原文永远不会被 `compacted-summary` 替换掉。
2. **已生成正文与历次改稿同为历史**，且近似重复，重复计费。
3. **token meter 按 4 字符/token 估算，会低估中文**，导致压缩阈值判断偏晚，往往到溢出才被动恢复。

结论：这不是"调压缩参数"能解决的问题，必须把小说从**对话状态**降级为**外部结构化资源**。

---

## 2. P1 要回答的问题

P1 要同时回答两个问题：

> **Q1（成本）**：能否用"离线结构化摄取 + 在线分层注入"，在续写质量不下降的前提下，让单轮输入 token 与全书字数解耦（O(1)）？
>
> **Q2（可移植）**：能否从同一份摄取产物导出**自包含概要**，脱离本插件、脱离原文，直接作为续写、或**单个事件/故事单元**的剧本化输入？

Q1 决定这个插件值不值得存在；Q2 决定它的产物有没有独立价值——概要一旦合格，用户即使不用插件也能用。

### 2.1 非目标（明确不做）

| 不做 | 原因 |
|---|---|
| 向量检索 / embedding 召回 | 强连续性任务上结构化状态优先；召回漏召会诱发编造设定。留到 P2 |
| 替换在线压缩后端 `dsh-compaction-basic` | 见 §6.4 决策点 D2：输入与全书长度解耦后在线压缩很少触发，替换后端的收益不足以承担影响面 |
| 多候选生成 / 模型路由 / 微调 | 与 P1 命题无关 |
| 改写用户历史消息 | 会话日志是唯一真相，任何改写必须可确定性重放；P1 用"不写入"代替"写入后再删" |

## 3. 方案总览

```
                     ┌──────────────── 离线（一次性 / 增量重跑）────────────────┐
  小说文件(分章)  →  切分(场景级)  →  内容清洗  →  显著度打分  →  章级卡片  →  卷级聚合  →  Bible
                     └───────────────────────────────────────────────────────────┘
                                                    │
                     ┌──────────────── 在线（每轮请求）─────────────────────────┐
                     │ L0 插件指令(不变)  → L1 全书Bible(卷更新) → L2 本卷摘要    │
                     │ → L3 最近3章卡片 + 最近1章原文节选(章更新) → L4 用户输入  │
                     └───────────────────────────────────────────────────────────┘
```

两个关键设计原则：

- **离线摊薄固定开销**：摄取用独立的小请求、不带对话系统提示，所以切得细几乎不增加成本；在线只读产物，不读全书。
- **分层缓存布局**：按"变动频率"排序，越稳定越靠前，使缓存失效只发生在尾部（详见 §7）。

离线链路还多出一条**导出支线**：

```
cards/ + bible.json  →  概要导出（profile × tier）  →  synopses/synopsis-<profile>-<tier>.md
```

它是同一份事实的第三种投影，**不是新的事实来源**（详见 §5.4）。三种产物各司其职：

| 产物 | 消费者 | 形态 | 用途 |
|---|---|---|---|
| `cards/` | 插件 | JSON | 机器装配上下文 |
| `bible.json` | 插件 + 模型 | JSON | 稳定设定前缀 |
| `synopses/*.md` | **人 + 任意外部模型** | 结构化散文 | **脱离本插件的可移植输入** |

### 3.1 文件布局与"两层切分"

一次性物理产物如下（`novels/<work>/`）：

```
novels/demo/
  source/full.txt        # 原样保留、只读，唯一真相
  chapters/ch0037.md     # 章级物理切分（模型可寻址读取的单元）
  manifest.json          # 章 → 行区间 / 字数 / 内容哈希 / 场景边界 / 叙事单元
  cards/ch0037.json      # 章级卡片（摄取产物）
  bible.json             # 全书 Bible
```

切分**分两层，粒度刻意不同**：

| 层 | 粒度 | 谁在用 | 为什么是这个粒度 |
|---|---|---|---|
| 物理切分（`chapters/`） | 章 | 模型 `read` | 每次 `read` 是一轮请求往返，章是往返次数与单次体量的最优平衡点 |
| 逻辑切分（`manifest.scenes`） | 场景 800–1500 字 | 摄取管线 | 脚本内是数组下标，没有往返成本，切细只有收益 |

`manifest.json` 承担四项职责：记录**场景边界**（供摄取使用，不物理切）、记录**内容哈希**（未变的章跳过摄取）、记录**行区间**（源文本被编辑时校验漂移）、记录**叙事单元**（`story_units`，供剧本化选中范围，见 §5.4）。它把"每次重算行偏移"这件易错的事，固化成一次性的、可校验的产物。

**两条来自评审的修正（v0.3）**：

- **物理切分粒度可变**：默认一章一文件，但在生成前预估"总章数 / 文件数 / 磁盘占用（按 2× 计）"并提示用户，允许改为每 N 章一文件（`chapterGroupSize`）。小文件过多时这是一次性成本，不必替用户拍板。
- **番外与"作者的话"按题材判断，不按体裁一律排除**：与主线属于同一故事、或涉及剧情/角色信息的，**纳入输入**；判定无关的不处理，并在 `manifest.json` 的 `excluded` 中记录排除理由，便于复核与回滚。

### 3.2 内容安全过滤（硬约束）

**要求**：概要及其所有下游产物**不得包含性行为过程的描写**。

**范围：唯一判据是内容，不是词**

| 级别 | 内容 | 处理 |
|---|---|---|
| L0 无 | 不涉及 | 原样保留 |
| L1 暗示 / 淡出 | "一夜过去""第二天她先醒了" | **保留**——这是剧情转折，丢掉会导致因果断裂 |
| L2 过程描写 | 对性行为本身的具体描写 | **过滤**，只留占位事实 |

**明确不做关键词过滤。** 两个理由：

1. 中文此类描写高度隐喻化（"云雨""春宵"、器官代称、纯动作白描），词表召回率很低；
2. "进入""插入""湿润""抽动"这类词在战斗、雨天、器械场景里完全正常，词表会大面积误伤。

**词表既漏又误，不能当判据。**

**三层处理**：

| 层 | 内容 | 谁在读 |
|---|---|---|
| L0 原文 | `.raw` 原样留存 | **不进入任何模型调用** |
| L1 清洗文本 | 敏感段整体替换为占位标记 | 摘要模型 |
| L2 卡片 | 只记录抽象事实 | 插件、概要、剧本 |

**占位而非删除**：被过滤的段落保留位置与边界，替换为

```
【第 N 段：亲密场景，已按内容策略省略，源行 1234–1256】
```

这样模型知道"此处发生过某事、时间线没有断"，但看不到内容。**直接删除会让剧情出现空洞，占位则保住因果链**——这是过滤与连贯性之间的关键取舍。

**判定机制：一次调用内完成"标记 + 抽取"**

卡片生成本来就是一次模型调用。把内容策略直接写进这次调用的指令，让它：

1. 先扫全章，标出属于 L2 的段落（输出行区间）；
2. 这些段落**不记录内容**，只写一句占位事实，进 `beats` / `summary`；
3. 其余段落正常抽取。

**占位事实**长这样：

```
【本章含性行为描写，已按内容策略省略；事件后果：两人关系变为恋人】
```

模型知道"发生了什么、导致什么"，产物里却没有任何过程描写。

**兜底：产物复核（小输入）**

卡片与概要生成后，用一次**低成本复核**判断产物是否含 L2 描写——输入只有几百 token 的产物本身，不是原文。命中则标记该章 `needs_regen` 并回退重生成，对应 **M18**。

复核之所以便宜且可行，是因为它只需判断"有没有"，不需要理解剧情。

**可选的预检（默认关闭）**

`preScreen: keyword` 可提供段落级粗筛，仅用于"先圈出候选段、缩小模型注意力"，**不参与任何最终判定**，默认关闭；开启后仍以内容判定为准。

**标题按同一判据处理**：本作标题多为擦边调侃（如"过来叉我吧"），属**暗示而非过程描写，保留**。只有当标题本身就描述了具体行为时，才脱敏为 `第 N 章（标题已省略）`。判断依据与正文一致，仍不用词表。

**对七个维度的影响**：

- **A 风格锚点**：选段时跳过敏感段，锚点只能取自清洗后的文本
- **C 人物关系**：可写"关系发生变化"，不写如何变化
- **D 剧情脉络**：只记录事件与其后果，不记录过程

> 过滤必然损失信息。取舍原则是**保留因果、丢弃细节**：读者需要知道"他们在一起了"，不需要知道别的。

## 5. 数据结构

### 5.1 章级卡片（`chapter_card`）

**两套预算，且按 `density` 分级**（v0.10 实测修正）：

| 形态 | 消费者 | 预算 | 实测（7 章） |
|---|---|---|---|
| **存储态**（compact JSON） | 聚合模型、关系图派生、校验器 | **按分级，见下** | 418 – 914 |
| **注入态**（渲染文本） | 对话上下文（L3 层） | **按分级，见下** | 186 – 409 |

| `density` | 判定 | 存储态上限 | 注入态上限 |
|---|---|---|---|
| < 0.6 | 过渡章 | 450 | 200 |
| 0.6 – 0.8 | 常规章 | 650 | 250 |
| > 0.8 | 高密度章 | 950 | 300 |

**为什么必须分级**：单一预算在均值上成立，在峰值上必破。第 84 章（最长章 6194 字、density 0.88）存储 914、注入 409，是均值（572 / 223）的 1.6 / 1.8 倍。**而高密度章恰恰是最不能丢信息的那一章**，用均值预算卡它等于系统性地牺牲关键章。

把 350 当成单一预算更是概念错误：卡片是**存储**的，进上下文的是**渲染后**的文本，两者差 2.6 倍。

字段总量按存储态控制（主字段 ≤ 上限 × 0.8，`ext` ≤ 上限 × 0.2）；注入态由渲染器负责，不靠砍字段达成。字段固定、缺失写 `null`（空值可省略），不允许自由发挥。

**结构：主字段 + 副字段命名空间**

```json
{
  "schema": 2,
  "chapter": 37,
  "title": "夜雨破阵",
  "source": { "file": "ch0037.md", "chars": 3120, "density": 0.72 },

  "time": { "story": "第三年春", "span": "当夜", "mode": "linear" },
  "pov": ["方少云"],
  "location": ["执法堂外院", "执法堂地牢"],
  "beats": ["主角潜入执法堂", "与柳三更交手，暴露身份", "夺取玄铁令"],
  "entities_new": [
    { "name": "柳三更", "kind": "person", "tag": "执法堂首座·反派" }
  ],
  "relations": [
    { "a": "主角", "rel": "hostile", "b": "柳三更", "since": 37 }
  ],
  "state_changes": [
    { "subject": "主角", "field": "power", "from": "凝气九层", "to": "筑基初期" }
  ],
  "items": [{ "name": "玄铁令", "change": "获得", "holder": "主角" }],
  "reveals": [{ "who": "主角", "fact": "柳三更是内鬼", "chapter": 37 }],
  "foreshadow": { "planted": ["玄铁令上的血纹指向北境"], "paid": ["F-03 玉佩来历"] },
  "hook": { "text": "玄铁令碎裂，露出半张地图", "type": "cliffhanger" },
  "contentRedactions": [
    { "startLine": 31, "endLine": 35, "reason": "l2-sexual-content" }
  ],

  "ext": {
    "urban": { "goal": ["争夺省赛名额"], "rank": ["进入主力阵容"], "rival": ["柳三更"] }
  }
}
```

**主字段与消费者对照表（新增字段必须先在此表有归属）**

| 字段 | 消费者 |
|---|---|
| `time` | Bible 时间线、剧本场次时间 |
| `pov` | 续写视角一致性、剧本分场 |
| `location` | Bible 当前所在地、剧本 |
| `beats` | 概要 D/E、M6 重建率 |
| `entities_new` | 关系图节点表、Bible 人物表 |
| `relations` | 关系图（§5.5） |
| `state_changes` | Bible 状态 |
| `items`（含 `holder`） | Bible 物品表、一致性 |
| `reveals` | M5 校验、认知状态推导 |
| `foreshadow` | Bible `open_threads` |
| `hook` | 概要 F（推进方向） |
| `contentRedactions` | 实验 8 复核、审计 |

**无消费者的字段不得加入。** 新增字段时必须同时提交它的消费者，否则视为冗余。

**受控词表（强制，出现表外值即判该卡不合格）**

| 字段 | 取值 |
|---|---|
| `entities_new.kind` | `person` / `place` / `org` / `item` / `concept` |
| `state_changes.field` | `relationship` / `identity` / `location` / `power` / `possession` / `health` / `status` |
| `relations.rel` | `kin` / `friend` / `ally` / `hostile` / `rival` / `lover` / `mentor` / `subordinate` / `acquaint` |
| `time.mode` | `linear` / `flashback` / `timeskip` |
| `hook.type` | `cliffhanger` / `reveal` / `reversal` / `quiet` |
| `ext.<pack>` | 必须已注册，见下 |

`entities_new.tag` 限"标签 + ≤12 字"，不承载长篇描述——细节归 Bible，卡片只留索引。

**副字段：`ext` 命名空间与品类包**

- `ext` 的 key 必须是**已注册**的 pack，未注册直接判该卡不合格；
- 允许多个 pack 并存（混合类型，如"修仙 + 恋爱"）；
- **`ext` 总预算 80 token 是硬顶**，超出必须砍 pack，**不许挤占 `beats`**；
- 每个 pack 有独立 JSON Schema，字段同样受控枚举。

**P1 上线的三个包**

`urban`（校园 / 职场 / 都市）

| 字段 | 含义 |
|---|---|
| `goal` | 比赛、考试、求职的进度 |
| `rank` | 战队或公司内的地位变化 |
| `rival` | 对手队伍或竞争者 |

`romance`（恋爱 / 言情）

| 字段 | 含义 |
|---|---|
| `affect` | 情感指向与强度变化（好感、吃醋、冷淡） |
| `misunderstanding` | 误会或心结的**埋与解** |
| `rival` | 情敌出现 / 退场 |
| `promise` | 约定与誓言（后文须兑现） |
| `intimacy` | 亲密度**分级**（仅等级、不记细节，与 §3.2 同源） |

`cultivation`（修仙 / 玄幻）

| 字段 | 含义 |
|---|---|
| `realm` | 境界、功法、灵根、瓶颈 |
| `breakthrough` | 突破事件 **+ 代价**（代价比结果更重要） |
| `artifact` | 法宝品阶、认主、反噬 |
| `sect` | 宗门地位、任务、贡献 |
| `karma` | 因果与仇怨（谁欠谁） |

**推迟到 P2**：`palace`（宫斗）、`isekai`（异世界）、`dao`（道心/心魔）、`lifespan`（寿元）

**明确不做**：完整知识矩阵（由 `reveals` 累积推导）、场景级字段（由 `manifest.scenes` + 原文支撑剧本化）

**品类怎么定**

摄取开始时对全书判定一次（前 5 章 + 章节标题特征），写入 `manifest.genre: ["urban", "esports", "comedy"]`；`Config.genreOverride` 可手工覆盖。**不逐章判定**——不稳定，且每章一次判断纯属浪费。

**`density` 的定义（v0.8 修正）**：衡量**信息增量**，不是"剧情推进得好不好"。

```
density = 归一化( 新增实体数 + 状态变化数 + 新伏笔数 + 不可逆事件数 ) / 章字数
```

判据是"这一章让世界状态改变了多少"，与爽不爽、有没有打斗无关。按此口径，第 2 章（引入彭风、生命网吧、BOS 网吧三个关键实体）应打 **0.7+**，而不是 0.45。

> `density` 只用于确定卡片预算与是否保留原文锚点，不进入模型上下文。

**实测依据（v0.10，7 章含两个极值）**

| 章 | 字数 | density | 存储态 | 注入态 |
|---|---|---|---|---|
| 9（最短） | 2083 | 0.45 | 418 | 186 |
| 1–5（常规） | 2180–4713 | 0.55–0.90 | 520–619 | 198–239 |
| 84（最长） | 6194 | 0.88 | **914** | **409** |

第 9 章验证了空字段路径：`entities_new: []`、`relations: []` 时渲染器正常降级，无报错、无占位噪声。

**渲染器必须带裁剪策略**：注入态超上限时，按 **`ext` → `reveals` → 低权重 `relations` → 折叠 `beats` 至 4 条** 的顺序丢弃，并在文件首行标记 `[已裁剪]`。存储态不裁剪——存储是事实，注入是视图。

**渲染器是独立组件**（`src/ingest/render.ts`），纯规则、零模型调用：

```
【第4章】一日｜视角:方少云/Lulu
地:先锋网吧、新前520教室、学生二食堂
· 彭风盯上Raver鼠标，方少云被迫起身
· 视角切Lulu：输掉比赛，又因点名赶回学校
...
新:Lulu(第一SCMM·好胜)、Kay(Lulu同伴·温和)
关系:方少云-敌对-Lulu；Lulu-友-Kay
钩:我要在星际中用叉叉活活叉死她
[urban] goal=赢下与HP的再战；rival=Lulu/HP战队
```

结论：**不要为了省 token 砍 `beats`**——砍字段解决不了问题（存储态才 572，其中约 1/3 是 JSON 键名开销），渲染器才是控注入的手段。

### 5.3 分层内容归属

| 层 | 内容 | 更新频率 | 预算 |
|---|---|---|---|
| L0 | 插件指令、卡片使用说明 | 不变 | ≤ 400 token |
| L1 | Bible：人物、体系、时间线、未回收伏笔 | 卷边界 | ≤ 3000 token |
| L2 | 本卷聚合摘要 | 每 20 章 | ≤ 400 token |
| L3 | 最近 3 章卡片 + 最近 1 章原文节选（风格锚） | 每章 | ≤ 1200 token |
| L4 | 用户输入 | 每轮 | 不设限 |

### 5.4 自包含概要（`synopsis.md`）

三种产物中唯一**给人、也给外部模型直接消费**的形态：把 `cards` 与 `bible` 压平成一个自包含文件，脱离插件、脱离原文也能直接使用。

**硬约束（可自动校验，见 M14）**：文件内不得出现内部 ID（如 `F-07`）、文件路径、对 `cards/` 的引用；所有指代必须自足。这条约束是"可直接作为输入"的技术定义。

**七个维度**——按"续写需要什么"反推，而不是按"小说有什么"罗列：

| 维度 | 内容 | 为什么必须有 |
|---|---|---|
| A 作品与风格 | 题材、人称、时态、章节长度习惯、文风要点 3–5 条、**原文锚点 2–3 段**（各 150–250 字） | 语感只能靠原文样本传递，任何摘要都替代不了 |
| B 世界观与规则 | 等级/力量体系及阈值、禁忌与代价、地理与势力 | 体系写错是续写最高频的硬伤 |
| C 人物谱 | 主角（目标/缺陷/底牌/当前状态）、核心关系人、反派动机与进度、**已退场名单** | 名单专用于防止"已死角色复活" |
| D 剧情脉络 | 分卷概要（每卷 100–150 字）、最近 3–5 章详细事件、当前时间与地点 | 远粗近细，与 §7 同一原则 |
| E 伏笔账本 | 未回收（埋设章/内容/预期回收方向）、已回收简表 | 决定续写能"接住"多少前文 |
| F 续写接入点 | 上一章结尾场景、未解决的即时冲突、**3 个合理推进方向** | "直接可用"的关键；给多个方向避免锁死模型 |
| G 剧本适配层（可选） | 场次表（场号/地点/时间/人物/目标/冲突/结果）、1–2 场完整示范戏、改编取舍说明、对白风格要点 | 仅 `profile: screenplay` 生成；**只覆盖选定的一个叙事单元** |

**两档 profile，用途与范围都不同**：

- `continue`：A–F，覆盖到指定章（默认最新）。用于续写，范围是"全书的最小充分上下文"。
- `screenplay`：**单元剧本包**，必须用 `scope` 指定**一个事件或故事单元**。内容 = 该单元相关的上下文子集（A/B/C/E 中与它相关的部分）+ 该单元剧情（D 的对应段）+ G。

> **明确不做：不提供"全书 → 剧本"的转换。** 剧本化只针对一个可拍摄的叙事单元。全书改编涉及集数规划与跨单元结构，属于另一个问题，且与 P1"降低上下文成本"的命题无关——把它混进来只会让 P1 既做不完也验不准。

**单元的规模：一个故事 = 一个可拍摄单元**

按"故事"划分，单个 `story_units` 边界可达 **~100 章**（约 30 万字）。这是刻意的选择——100 章恰好接近一部电影或一季剧的体量。

但它带来一个硬约束：**100 章原文约 20 万 token，进不了任何上下文窗口**。所以剧本化必须走**三层压缩**，而不是"把单元塞进去"：

```
cards[unit range]  →  单元摘要 units/<id>.md  →  场次表 + 1–2 场示范戏
  100 × ~200 token      一次调用：输入 ~20k       一次调用：输入 ~5k
                        输出 3–5k
```

`units/<id>.md` 是独立可缓存的中间产物：再次生成剧本不必重读 100 张卡片。

**P1 的产出范围：场次表 + 示范戏，不含剧本全文。** 60 场的完整剧本约 6–9 万字，超出单次输出能力，必须分幕批次生成——那是 P2。P1 只证明"这个单元可以拍"，不交付成品剧本。

**单元怎么选**（`scope` 二选一）：

```jsonc
{ "chapters": [37, 45] }        // 章区间：用户清楚要改哪一段
{ "storyUnit": "秘境试炼" }      // 具名单元：从 manifest.story_units 中选
```

`story_units` 由摄取阶段给出**自动初稿**——按"主要目标达成 / 地点转移 / 主要反派更替 / 章末钩子收束"切分——并写入 `manifest.json`，**允许人工校正**。自动识别不准是常态，所以人工校正能力是 G 段的组成部分，不是事后补丁。

`scope` 缺失时 `novel_synopsis` **直接失败**并列出可选单元——不猜、不默认全书。

**三档预算**：

| 档位 | 预算 | 适用场景 |
|---|---|---|
| `compact` | ~2000 token | 短篇、试读、成本敏感 |
| `standard` | ~6000 token | 默认 |
| `full` | ~20000 token | 长篇精细改编、剧本 |

> 注意区分：§7 的分层是**在线注入**的装配顺序（为缓存服务）；本节是**离线导出**的独立文件（为可移植服务）。两者同源——都以 `cards` + `bible` 为唯一事实，因此不会互相漂移。

**形态取舍**：纯散文好读但查不住关键事实，纯结构化好查但模型续写时语感弱。采用**结构化骨架 + 散文填充**：每个维度一个标题，骨架字段用列表，剧情段与风格描述用短段落。原文锚点保持原样，不做任何改写。

**生成模式：投影型 vs 富化型（v0.4 定案）**

判断依据是**"是否需要新事实"**，不是"是否需要调用模型"——把同一批事实重新润色成散文，不算附加事实。

| 维度 | 事实来源 | 类型 | 默认 |
|---|---|---|---|
| B 世界观 | `bible.system` | 投影 | 生成 |
| C 人物谱 | `bible.characters` | 投影 | 生成 |
| D 剧情脉络 | `cards.beats` + 卷聚合 | 投影 | 生成 |
| E 伏笔账本 | `bible.open_threads` | 投影 | 生成 |
| A 风格锚点 | `bible.work.style_anchors` | 投影（前提：摄取时已保存原文片段） | 生成 |
| F 推进方向 | 基于前文**推断**（原文没有的走向） | **富化** | 不生成，按需 |
| G 剧本适配 | 重新分析结构 | **富化** | 不生成，按需 |

**关键约定：让投影型永远完备。** 把"概要所需的最小事实集"写进**摄取契约**——`style_anchors` 至少 2 段、每章 `hook` 必填、`open_threads` 必须存在。契约成立后，投影型概要**永远可以零询问直接生成**，不必等到运行时才发现缺口。这也是把完备性前移到摄取阶段的收益。

**三段判定**：

1. **本地完备性检查**（不调模型）：`style_anchors ≥ 2`？卡片覆盖 `1..N`？`open_threads` 存在？
2. 完备 → `projection` 模式，**直接生成**，不打断用户。
3. 不完备，或请求 `screenplay` / `full` / 显式要 F 推进方向 → 报告缺口与代价，**询问用户**。

**投影型的时点：按资源消耗量决定（v0.6 定案）**

- 预估总 token（输入卡片 + 输出预算）**≤ `eagerSynopsisBudget`（默认 20000）** → **摄取完成后立即落盘**，用户马上能看到成品。
- **超过阈值** → **延迟到第一次续写请求时生成**，成本并入那次请求；首次续写会额外等待，需提前提示"首次续写将先生成概要，约 X 秒"。

这样小书即刻可用，大书不为"可能用不到"的概要先付费。用户显式调用 `novel_synopsis` 时则立即生成——主动请求意味着成本在预期内。

**询问时必须给三个选项**（只问"要不要"是坏体验）：

```
缺口：
  - 风格锚点缺失（需回读 2 章原文）      约 +2 次调用 / 6k token
  - 第 40–52 章尚未摄取                  约 +13 次调用 / 26k token / 约 8 分钟

[仅生成可投影部分]  [补全后生成]  [取消]
```

第一个选项保证**总有可用产物落地**，不会因为缺口把用户卡死。

### 5.5 轻量关系图（`graph.json`）

**先回答"图给谁用"。**

模型不读图。模型读文本。把图的 JSON 塞进 prompt 只会更贵、更难懂，对模型没有直接价值。

图的价值全部在**插件侧**，落成四种可执行操作：

| 操作 | 用在哪儿 |
|---|---|
| 查询"这一单元涉及哪些人物、彼此什么关系" | 剧本人物表（M13） |
| 校验"已死亡角色是否再次出场""关系突变有无过渡" | 一致性检查（M5） |
| 增量更新（只加边、改边，不重写文本） | 368 章的累积维护 |
| 渲染成邻接表 | Bible 人物表、概要 C 维度 |

所以结论：**存，但它不是事实来源，也不是第四种投影——它是从 `cards.relations` 按章累积出来的派生索引。**

**为什么不让模型直接写图**

模型输出三元组的错误率很高：同一人物出现别名、关系方向搞反、时间混乱。而"A 是 B 的前女友"与"A 是 B 的女友"在图上会变成两条互相冲突的边。

对策两条：

1. **图只从卡片派生**。`relations.rel` 是受控枚举，`a`/`b` 必须已存在于节点表或本章 `entities` 中，规则即可校验，无需模型再判一次；
2. **边带时间区间，不做覆盖。**

**修正（v0.11）：放弃"廉价规则第一遍"，改顺序单遍**

第 84 章出现了约 14 个人名，单看一章无法判断谁是新角色——`entities_new` 天然依赖一个既有集合。原计划用规则扫一遍建 `nodes.json`，**实测失败**：

| 名称 | 全文实际出现 | 规则命中 |
|---|---|---|
| 方少云 | 13,127 | 888 |
| 纳兰容容 | 550 | 0 |
| 彭风 | 260 | 0 |
| 小雨 | 144 | 0 |

原因很具体：**这本小说的对话大量不带说话人标记**。"彭风说："全文只出现 3 次，绝大多数是"彭风等人""彭风一伙"。基于"名字 + 说/道"的规则召回率不到 10%，**不能作为依赖**。

改为**顺序单遍**：

- 逐章抽取，第 N 章拿到的是前 N−1 章累积的节点表；
- 抽完回写节点表，供下一章使用；
- **放弃并行**——368 章串行即可，离线批处理不需要并行。

代价是墙钟时间；收益是**只读一遍原文**（两遍法要读两遍，成本翻倍）。对 368 章的规模，这个交换划算。

**规则保留，但只做校验**：ASCII ID 的规则很准（Lulu 实测出现 4,848 次、规则命中 4,852），可用于交叉核对模型产出，不用于依赖。

**时序边是关键**

关系会变，而这正是这类小说的核心张力。边不是 `A -[lover]-> B`，而是：

```json
{ "a": "方少云", "rel": "lover",   "b": "小雨",   "fromChapter": 1, "toChapter": 1 },
{ "a": "方少云", "rel": "acquaint","b": "Lulu",   "fromChapter": 4, "toChapter": 4 },
{ "a": "方少云", "rel": "hostile", "b": "Lulu",   "fromChapter": 4, "toChapter": null }
```

`toChapter: null` 表示当前仍有效。这样"前女友"不会覆盖"女友"，而是同一对节点上的两段边，历史不被抹掉。这也补上了 `state_changes` 的短板——它只能记 `from → to`，会丢中间态。

**明确不做**（防过度工程）

- 不做传递闭包、不做推理（"朋友的朋友"没有产品需求）
- 不上 RDF / OWL，就是节点表 + 邻接表
- 不引图数据库，一个 JSON 文件够用到百万字量级

**规模估算**：368 章、人物约 200、边约 600（含历史段）。JSON 约 60–100 KB；渲染成 Bible 人物表后 ≤ 800 token。

**与卡片预算的关系**：`relations` 是"用结构化换自由文本"——单条三元组约 12 token，比塞在 `entities.tag` 里的关系描述更省，且可校验。这也是卡片能压到 350 的来源之一。

## 6. 插件形态与扩展点

### 6.1 包与装载

Host-only bundle，`dsh.bundle.patch` 插入一行：

```yaml
- insert:
    - id: novel-helper
      name: 'dsh-novel-helper'
      config:
        novelDir: 'D:/codetest/novels/demo'
        recentChapters: 3
        bibleTokenBudget: 3000
        cardBudgetTokens: 250
        chapterGroupSize: 1            # 物理切分粒度：每 N 章一文件（可变，生成前提示）
        diskEstimateMultiplier: 2      # 磁盘占用按 2× 预估并提示
        synopsisProfile: continue      # continue | screenplay
        synopsisTier: standard         # compact | standard | full
        synopsisMode: auto             # auto：投影型直接生成，富化型才询问；never：只出投影型
        eagerSynopsisBudget: 20000     # 投影型预估 ≤ 此值则摄取完即落盘，否则延到首次续写
        contentPolicy: l2-only         # 只过滤性行为过程描写；L1 暗示保留
        preScreen: none                # none | keyword；仅缩小候选段，不参与判定
```

导出形如：

```js
export const Config = /* schema，字段同上，含默认值与校验 */
export const inject = ['tools', 'systemPrompt']
export function apply(ctx, config) { /* 所有注册经 ctx.effect / ctx.on 并返回清理函数 */ }
```

### 6.2 工具

| 工具 | 作用 | 说明 |
|---|---|---|
| `novel_ingest` | 摄取/增量摄取指定章节范围 | 幂等、可断点续跑；返回已覆盖章节与失败章节 |
| `novel_status` | 查看覆盖进度、卡片统计、预算占用 | 不触发模型调用 |
| `novel_context` | 按需取出指定章范围的卡片（+ 可选原文节选） | 给模型一个"多要一点"的出口，替代 P1 的检索 |
| `novel_synopsis` | 导出概要：`{ profile, tier, scope?, uptoChapter?, enrich? }` | **P1 的核心交付**；`profile=screenplay` 时 `scope` **必填**（单元剧本包，不做全书）。`enrich: false`（默认）只做投影、不询问。落盘 `synopses/*.md`，返回字数与 token 估算 |

### 6.3 注入

- **L0 + L1**：`ctx.systemPrompt.section()`。二者均为低频变动，落在请求前缀，是缓存收益的主要来源。
- **L3**：`agent.inject()`，每章切换时注入一次。**不订阅 `agent/pre-step` 去改写历史消息**，避免破坏日志可重放语义。
- **L2**：随 L1 一同更新，或作为 L3 的头部。

### 6.4 可寻址读取：为什么必须先切分

`read` 按**行**分页：`offset` 是行号，`limit` 默认 2000 行。一部 30 万字的小说无法一次读完，"一次性读取"的真实形态是连续多次 `read` 往后翻页。这个形态有三个问题：

1. **全量 token 照付**，一分不省；
2. **每翻一页就是一轮工具往返**，每轮都要重发此前全部历史；
3. 内容落进会话日志后**无法回收**——压缩契约不允许切分单个大单元，工具结果裁剪也只保留开头 4096 + 结尾 1024 字符，且原文永久留在日志里。

因此插件**不提供"把小说读进上下文"的路径**，只提供按章寻址：

| 约束 | 做法 |
|---|---|
| 模型只读章文件 | `chapters/chNNNN.md`，一章一次 `read` |
| 不再细切 | 场景级文件会让一次续写变成 3–5 轮往返，反而更贵 |
| 行偏移不重算 | 由 `manifest.json` 固化，源文本变更时用哈希校验 |
| 越界读取 | 由 `novel_context` 按章范围返回，不鼓励模型自行猜 `offset` |

> 规则：**离线内部细，在线读取粗。** 摄取管线按场景切（无往返成本），模型读取按章切（往返成本高）。

### 6.5 决策点（v0.3 已确认）

以下三条已由评审确认，结论汇总在 §12，此处保留理由。

**D1｜Bible 与卡片存放在哪。** 备选：(a) 工作区文件（用户可见、可手改、易调试）；(b) 平台存储服务（经 `cordis_inspect_query` 确认后使用，会话隔离更好）。**建议 (a)**，P1 以可调试性优先。

**D2｜是否替换在线压缩后端。** 建议 **P1 不替换**。理由是 P1 的前提就是让输入与全书长度解耦，一旦成立，在线压缩在小说会话里将很少触发；替换 `CompactionEngine` 影响面覆盖所有会话，且需要接管 bracket 事务与失败语义，投入产出比不成立。若实测仍频繁触发，作为 P1.5 单独立项。

**D3｜"小说专用 `summarize()`"落在哪。** 明确：**只用于离线摄取管线**（我们自己发起的模型调用，模板与预算完全自控），不是替换引擎的 `summarize()` 钩子。这样既拿到领域模板的收益，又不承担引擎级影响面。

## 7. 缓存分层布局

原则：**越稳定的内容越靠前；缓存失效只应发生在尾部。**

```
[系统提示 L0][Bible L1][卷摘要 L2] ── 稳定区，跨轮/跨章复用
[最近3章卡片 + 1章原文 L3]        ── 每章变一次
[用户本轮输入 L4]                 ── 每轮变
```

由此得到三条实现约束：

1. Bible 更新只发生在**卷边界**，且新增内容追加在段末，避免中部插入导致后半段全部失效。
2. L3 每次只加一章、丢一章，不做整段重排。
3. 任何"为了省 token 而中途改写早期消息"的行为一律禁止——它会让缓存收益归零。

## 9. 实验设计

**实验 0｜切分边界准确率（前置门禁）**
抽 50 章（含卷首、卷末、番外各若干），核对 `chapters/` 的物理边界与 `manifest.scenes` 的逻辑边界：章切分是否落在真实章节边界、场景边界是否至少不把一个完整场景劈开。统计**边界错切率**（切错或漏切的行数 / 总行数）与**章数偏差率**（|切出章数 − 实际章数| / 实际章数）。任一超阈值 → 先回到格式规整，不进入后续实验。

**实验 1｜卡片重建（离线）**
抽 20 章（覆盖高/中/低三个密度档），仅给评审者看卡片，要求回答：谁登场、他变化了什么、得到/失去了什么、埋了什么、结尾钩子是什么。统计 5 项全中的比例。

**实验 2｜续写一致性（A/B）**
固定 10 个章节开头，同一模型分别以「基线：粘贴全书」与「P1：分层注入」续写 2000 字。由评审（用户本人）标注硬伤。**同模型同参数**，仅上下文不同。

**实验 3｜成本与有界性**
记录每次请求的输入/输出/缓存命中 token。分别用 10 万字与 100 万字的书各跑 5 章，检验 M1。用 `performanceUsage: detailed` 的现成统计取数。

**实验 4｜可重放与隔离**
小说会话执行 `fork`，比较注入内容哈希；另开一个纯代码会话，确认工具不可见、系统提示无插件文本、token 无增长。

**实验 5｜冷启动续写（终验，M12）**
最严苛的一条：**新开会话、不加载插件、不提供原文、不提供任何历史**，只把 `synopses/synopsis-continue-standard.md` 粘进去，配一句"接着写 2000 字"。由评审按三档打分（直接可用 / 小改可用 / 不可用），并统计硬伤。这一条通过，才说明概要真的"可以直接作为输入"。

**实验 6｜单元剧本化（M13、M16、M17）**
先由插件对一部书自动切分 `story_units`，人工核对 20 个边界点（得 M16）。再选其中 2 个单元——**至少一个达到 ~100 章规模**——只给对应的 `synopsis-screenplay-*.md`，要求输出"场次表 + 一场完整戏"。检查：要素齐全度、可拍摄性、场次表是否被截断（M17），并确认产出**只覆盖该单元、没有蔓延到全书**。

**实验 7｜生成路径判定（M15）**
构造 10 个 fixture 覆盖：事实完备、缺风格锚点、缺后段章节、请求 `screenplay`、请求 `full`、显式 `enrich`。核对三件事——投影型是否零询问直接出文件；富化型是否**必须先确认**；「仅生成可投影部分」是否总能产出可用文件（不允许空手而归）。

**实验 8｜内容策略（M18）**
用**产物复核**（内容判定）扫全部产物；另抽 10 章人工复核，确认三件事：占位事实没有泄漏可推断的细节；L1 暗示段（"一夜过去"）被正确保留；时间线与因果仍然成立（过滤没有把剧情切断）。

**判定规则**：实验 0（M11）未通过 → 一票否决，先修格式规整。M1、M2、M5、M6、M8、M9、M12、M14 全部通过 → P1 达标；M13 未达标但其余通过 → 记为"续写达标、剧本待补"，剧本适配层转入 P2。M3/M4 未达标但其余通过 → 记为"达标但有优化空间"，进入 P1.5 讨论。

## 11. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 摄取摘要失真，卡片漏关键事实 | 直接影响 M5 | 固定字段 + 抽取优先于生成；M6 做量化门禁 |
| 姓名/称谓在卡片中被规范化过头 | 续写时称谓错乱 | 卡片保留 `aliases` 原样；Bible 不做同义合并 |
| 规则打分误判密度 | 高信息段被粗切 | 打分只决定预算，不决定是否切；高分段强制保留原文锚点 |
| 章节标题格式不统一（无标题、番外、作者的话混入正文） | 边界错切，污染卡片与 Bible | 实验 0 前置门禁；提供手工边界表 `manual-boundaries.json` 兜底 |
| 长书（100 万字+）首次摄取耗时 | 上线体验差 | 按卷生成、优先摄取最近章节；支持边写边补 |
| 插件影响非小说会话 | 卸载成本高 | M9 作为准入项；提示与工具仅在检测到小说目录配置时注册 |
| 概要"压平"时聚合失真（错误集中暴露在单一文件里） | Q2 直接失败 | M14 全自动校验 + 实验 5 冷启动终验做兜底 |
| 概要过长用户不敢用、过短又不够用 | 产物形同虚设 | 三档预算并存，用实验 5 实测定默认档 |
| 剧本适配层是启发式，可能给出不准的改编建议 | 误导用户 | G 段一律标注"建议"，不写成结论 |
| 自动识别叙事单元边界偏差 | 剧本范围跑偏（漏场、串场） | M16 量化；`manifest.story_units` 可人工校正后重生成；`scope` 支持直接用章区间绕过自动识别 |
| 100 章单元的场次表超出单次输出上限 | 剧本产物被截断 | M17 门禁；场次表按幕分片生成，合并时校验场号连续；P1 只承诺场次表 + 示范戏 |
| 磁盘占用预估偏低 | 用户磁盘被动占用 | 按 2× 预估并在生成前确认 |
| 卡片三元组质量差（别名、方向反、时间错） | 关系图失真，连带 M5 失效 | `rel` 受控枚举 + `a`/`b` 必须在节点表内，规则可校验；M19 抽检 20 条 |
| `density` 按"信息增量"打分会把过渡章打低 | 过渡章卡片过粗，丢失人物/地点引入 | 新增实体本身计入增量，过渡章只要有新实体就不会被压到最低 |
| 品类误判导致选错 pack | 字段空转，或关键信息无处落 | `Config.genreOverride` 可手工覆盖；M20 用"连续 5 章全空"触发复判 |
| `ext` 挤占主字段预算 | `beats` 被压缩，M6 重建率下滑 | 270 + 80 硬切分，校验器直接拒绝越界卡片 |
| 字段膨胀（每加一个 × 368 章都是永久成本） | 卡片重回 676 token 的翻车 | 新增字段必须先登记消费者；无消费者不加（§5.1 对照表） |

## 12. 评审结论（v0.11，全部收敛）

| # | 问题 | 结论 |
|---|---|---|
| 1 | 存储位置 | **工作区文件**。插件运行前预估占用空间并按 **2×** 提示用户（`diskEstimateMultiplier: 2`，见 §6.1） |
| 2 | 是否替换在线压缩后端 | **接受不替换**；领域模板只用于离线摄取（D2/D3 定案） |
| 3 | 番外 / 作者的话 | 不按体裁一律排除：与主线**同一故事**、或涉及**剧情/角色信息**的纳入输入；判定无关的不处理，并在 `manifest.excluded` 记录理由 |
| 4 | 评测人力 | 由用户本人担任评审（实验 2/5/6 的标注人） |
| 5 | M3/M4 目标值 | **接受**"待基线校准" |
| 6 | 物理切分粒度 | **可配置可变**：生成前提示章数/文件数/空间，允许选每 N 章一文件（`chapterGroupSize`） |
| 7 | 概要生成时机 | 判据是"是否需要新事实"，不是"是否调用模型"。**投影型直接生成，富化型先询问**（详见 §5.4） |
| 8 | 投影型的落盘时点 | **按资源消耗量划分**：预估 ≤ `eagerSynopsisBudget`（默认 20000 token）→ 摄取完即落盘；超过 → 延到首次续写时生成，成本计入那次请求 |
| 9 | 剧本范围 | **保留 G 段，但只做"单个事件/故事单元"的剧本化，不提供全书→剧本**。`scope` 必填，缺失即失败 |
| 10 | 单元粒度 | **按"故事"划分，单个单元可达 ~100 章**。因此剧本化走三层压缩（卡片 → 单元摘要 → 场次表），P1 只交付场次表 + 示范戏 |
| 11 | "可用"判定口径 | 三档（直接可用 / 小改可用 / 不可用）；阈值 **续写 80%**、**剧本 70%** |
| 12 | 内容安全 | **只过滤性行为过程描写（L2），判据是内容不是词**；L1 暗示/淡出保留。词表既漏又误伤，不作判据。清洗在模型调用前完成，以占位事实代替，由 M18 兜底（详见 §3.2） |
| 13 | `density` 口径 | **衡量信息增量**（新增实体 + 状态变化 + 新伏笔 + 不可逆事件），与"剧情推进得好不好"无关（详见 §5.1） |
| 14 | 人物关系是否建图 | **建，但只作插件的派生索引**，不喂给模型。从 `cards.relations` 累积成时序边，用于剧本人物表、一致性校验与 Bible 渲染（详见 §5.5） |
| 15 | 卡片字段分主副 | **主字段 ≤270 token + `ext` 副字段 ≤80 token**，硬切分。新增字段必须先在"消费者对照表"登记，无消费者不加（详见 §5.1） |
| 16 | 品类包范围 | P1 上线 `urban` / `romance` / `cultivation` 三个包；`palace` / `isekai` / `dao` / `lifespan` 推迟 P2。品类**全书判一次**，支持手工覆盖 |
| 17 | 卡片预算怎么算 | **分存储态与注入态两套，且按 `density` 分级**（450/650/950 对 200/250/300）。不为省 token 砍 `beats`；注入靠渲染器按优先级裁剪，不靠字段裁剪（详见 §5.1） |
| 18 | 抽卡能否并行 | **顺序单遍**：逐章抽取并递推累积节点表，放弃并行。规则第一遍已实测失败（中文名召回 <10%），只保留 ASCII ID 规则做交叉校验（详见 §5.5） |

### 12.1 仍需输入

唯一的阻塞项：**1–2 章真实样本**。切分器的章节标题正则、"番外是否同一故事"的判定依据，都只能从真实格式里得出。没有样本，W1 的切分器只能按假设写，返工风险集中在实验 0。
